# 技术文档

版本 0.1.0-beta ｜ 平台 Windows 10/11 x64 ｜ 语言 Python 3.10+（开发与实测在 3.13）+ CustomTkinter

---

## 1. 选型

| 方案 | 结果 |
| --- | --- |
| C# / .NET WPF | **放弃**：需要安装 SDK，构建链重，引入运行时依赖 |
| Electron / Tauri | **放弃**：体积与内存占用过大，违背「降低开销」第一优先级 |
| Python + tkinter | **采用**：依赖极简，Win32 调用走 ctypes 直接封装 |

最终依赖只有 `customtkinter` 一个第三方包。输入相关全部用标准库 `ctypes`
直接调用 Win32，**不依赖 pywin32 / pynput / keyboard**——这三个包要么有额外
依赖，要么内部又套了一层线程与轮询，会增加开销与不确定性。

---

## 2. 线程模型

```
主线程             Tk 事件循环
   │  每 25ms 队列泵（唯一操作控件的线程）
   │
   ├── input-hook 线程   键盘低级钩子常驻 + 录制时挂鼠标钩子
   │                     只做「写入数组」和「往队列塞命令」
   │
   └── player 线程       回放，只做注入 + 往队列塞进度
```

两条规则保证了界面永不因钩子或回放卡顿：

1. **钩子回调里绝不碰控件**。快捷键只往 `queue` 塞一个字符串命令。
2. **回放进度经队列节流到 20Hz**。回放线程不调用任何 Tk API。

`queue.Queue(maxsize=4096)` 满时用 `put_nowait` + 捕获 `queue.Full` 丢弃，
不会因界面卡住而反压回放线程。

## 3. 录制

### 3.1 钩子

`WH_KEYBOARD_LL` / `WH_MOUSE_LL` 低级钩子，装在专用线程上，
线程内跑 `GetMessageW` 消息循环——**阻塞等待，空闲 CPU 为 0**，不是轮询。

- 键盘钩子**常驻**：全局快捷键在未录制时也要能用。
- 鼠标钩子**按需装卸**：只在录制期间挂载，空闲时系统少一个钩子。
- **装卸都发生在钩子线程内部**：UI 线程只经 `PostThreadMessageW(WM_APP+x)`
  投递请求。低级钩子回调只在安装线程泵消息时触发——装在 UI 线程上，
  主线程一卡（打开大脚本、统计计算）钩子就会超时丢事件；钩子线程跑着
  GetMessageW 死循环，回调永远能及时执行。

### 3.2 事件存储

事件不建对象，直接写进 `array('i')`，每条 6 个 int32 = 24 字节：

| 字段 | 含义 |
| --- | --- |
| 0 | kind：0 键按下 / 1 键抬起 / 2 鼠标移动 / 3 鼠标按下 / 4 鼠标抬起 / 5 滚轮 / 6 横向滚轮 |
| 1 | a：按键=虚拟键码；鼠标键=按钮号；滚轮=增量；移动=X |
| 2 | b：按键=扫描码；移动=Y |
| 3 | c：按键=扩展键标志 |
| 4 | dt_us：距上一条的微秒数 |
| 5 | 预留 |

10 万条 = 2.29 MB，100 万条 = 22.9 MB。`array.append` 分块增长，不做整表复制。

### 3.3 时间戳

用 `time.perf_counter_ns() // 1000`（微秒，单调时钟）。
不用钩子结构体里的 `time` 字段——它是 32 位毫秒，49.7 天回绕，且精度只有毫秒。

`dt_us` 落在 i32 里，上限约 35.8 分钟；录制时超过 30 分钟的停顿按 30 分钟记
（防溢出截断：长会议/挂机场景下脚本的「总时长」会相应缩短，属已知取舍）。

### 3.4 鼠标移动采样

移动事件占真实录制的 80% 以上，是事件量的主要来源。两级阈值过滤：

- 最小间隔（默认 8ms）：比上一条移动点近的丢弃
- 最小距离（默认 2px）：位移不足的丢弃

**按键与点击类事件从不采样**，一定全量记录，保证点击时序精确。

### 3.5 自身事件过滤

钩子检查 `LLKHF_INJECTED` / `LLMHF_INJECTED`，默认忽略本程序注入的事件，
避免回放被自己录进去、以及注入事件触发快捷键造成自激。

## 4. 回放

### 4.1 绝对时间轴

```
target = t0 + 累计dt / 倍速
```

每条事件都按**绝对时刻**校准，不是「睡够间隔就发下一条」。
因此单条事件迟到不会累积成漂移；实测 3000 条 × 4ms 漂移 +0.4ms。

倍速可在回放中实时调整：还没等完的剩余时间按新旧倍速等比换算重定基线，
立即生效且不重走已等过的时间。

### 4.2 等待策略（本项目的核心性能决策）

朴素写法是「`time.sleep` + 末段自旋」，自旋期间该 CPU 核心 100% 占用。
改用 **`CreateWaitableTimerExW` + `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`**
（Win10 1803+）：等待期间线程真正挂起，只在最后 0.2ms 自旋收口。

实测对照（3000 条 × 4ms，共 12s）：

| 策略 | 漂移 | CPU | 每条开销 |
| --- | --- | --- | --- |
| sleep + 自旋 0.5ms | +0.9ms | 7.55% | 302 µs |
| 定时器，纯等待 | +0.6ms | 0.78% | 31 µs |
| **定时器 + 自旋 0.2ms（采用）** | **+0.4ms** | **1.82%** | **73 µs** |
| 定时器 + 自旋 0.5ms | +0.4ms | 5.86% | 234 µs |

逐条落点精度（4000 条 × 4ms）：

| 自旋窗口 | 中位 | P95 | P99 | 最大 | CPU |
| --- | --- | --- | --- | --- | --- |
| 0 | +0.335ms | +0.609ms | +0.740ms | +1.049ms | 0.98% |
| 0.05ms | +0.270ms | +0.524ms | +0.605ms | +0.776ms | 1.07% |
| **0.2ms（采用）** | **+0.162ms** | **+0.418ms** | **+0.501ms** | **+0.883ms** | **1.37%** |
| 0.5ms | +0.000ms | +0.042ms | +0.148ms | +0.310ms | 6.84% |

取 0.2ms：P99 落点误差 0.5ms（远小于一帧 16.7ms），CPU 只有 1.4%。
0.5ms 能把落点压到 0.04ms，但 CPU 涨到 6.8%，对游戏机箱里的 CPU 占用不值当。

同时**不再无条件调用 `timeBeginPeriod(1)`**：它会抬高全系统定时器中断频率。
只有在拿不到高精度定时器时才作为兜底启用。

### 4.2.1 等待必须可被打断

所有间隔（含数分钟的长停顿）一律挂在可等待定时器上，不再按 50ms 分界退回
`time.sleep`——那会让长停顿中的暂停/停止按键迟迟不生效（以前最长要等 60 秒）。
定时器句柄与 stop / resume 两个手动复位事件一起 `WaitForMultipleObjects`：
任何时刻的暂停、停止请求都能在毫秒级打断等待。被打断的一侧调用
`CancelWaitableTimer` 取消尚未触发的定时器，避免残留信号让下一次等待立即空过。

### 4.3 暂停 / 继续

暂停时**主动抬起所有按下的键盘键和鼠标键**，继续时把「暂停瞬间仍按着的键」
重新按下（保持原按下顺序）。不这么做，暂停期间目标程序里会出现按键卡死、
或按住左键拖着鼠标乱跑的异常；「长按前进」这类动作也能在暂停干预后接续。

继续后重新校准时间轴基线（`t0 = now - 已耗时`），暂停时长不计入；
正在等待中的那个间隔在继续后重新完整等待。

停止/异常退出路径同样会抬起所有仍按下的键（`finally` 兜底），
且停止请求能从任意长度的等待中即时打断（见 4.2.1），
关窗时不会出现「线程睡在长间隔里、按键悬挂在按下状态」的情况。

### 4.4 从已执行位置继续

回放位置实时记录在 `_executed`。点「从已执行位置继续」即
`play(script, start_index=_executed)`。

从中间开始时，起点之前就按下的键不会被复现——这是有意为之：
脚本本身不记录「起始状态」，凭空中途按下某个键反而危险。

### 4.5 收尾

无论正常结束、停止还是异常，`finally` 里都会抬起所有仍按下的键与鼠标键，
不会把键盘鼠标丢在按下状态。

## 5. 数据格式

见 README 的「脚本文件格式」。要点：

- 定长 24 字节记录，`array.tofile` / `frombytes` 直接整块读写，
  **不走 Python 循环**，10 万条读取 2.5ms。
- zlib 压缩，实测压缩比约 12:1（`dt_us` 的低字节多为 0，压缩率很高），
  100 万条约 120KB。
- 原子写入：先写 `.tmp` 再 `os.replace`，中途断电不会留下半个文件。
- 带格式版本号，未来加字段可以拒绝旧版本而不是读出乱码。

## 6. 坐标

- 进程声明 **DPI 感知**（`SetProcessDpiAwarenessContext(-4)`，即 per-monitor v2）。
  必须在创建任何窗口、安装钩子之前调用。
- 坐标按**物理像素**记录，与目标程序内坐标一致。
- SendInput 用 `MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK`，
  把物理像素映射到 0..65535。
- 换算公式按 `宽-1` 归一化，保证右下角正好映射到 65535。
  实测往返误差 0.02px。

### 曾经踩的坑（已修）

`_VSCREEN` 最初在模块导入时求值：

```python
_VSCREEN = virtual_screen()   # ← 错误
```

模块导入发生在 `set_dpi_awareness()` **之前**，于是缓存下的是被系统按缩放
虚拟化过的尺寸。后果是注入坐标系统性偏移，点击全部打偏。
现改为首次使用时惰性求值，并在录制开始、回放开始前主动刷新。

## 7. 滚轮编码（约定不一致，必须区分）

同一份 `mouseData`，两个方向的约定**不同**：

| 方向 | 约定 |
| --- | --- |
| 录制（钩子回调读到） | 滚轮增量在 **高 16 位** |
| 回放（SendInput 传入） | 按 **有符号 32 位整数**解释，并被系统夹到 ±32767 |

### 曾经踩的坑（已修）

回放侧最初写成「高低 16 位都写上增量，兼容两种解析」：

```python
word = delta & 0xFFFF
data = (word << 16) | word     # ← 错误
```

系统把它当有符号 32 位读，`0x00780078` = 7864440，远超 ±32767 于是被夹成
32767，滚轮方向和格数全错。实测：

```
注入 双写 +120 (0x00780078) -> 钩子读到 32767   ← 错
注入 低字 +120 (0x00000078) -> 钩子读到   120   ← 对
注入 双写 -120 (0xFFFFFF88) -> 钩子读到  -120   ← 对
```

正确做法是直接传有符号增量本身（`+120` → `0x00000078`，`-120` → `0xFFFFFF88`）。
`selftest.py wheel` 会持续守住这条。

## 8. 界面

CustomTkinter 三页，深色主题。

- **录制页**：大号状态与计时，一个主按钮。
- **脚本与回放页**：信息条（条数/时长/内存/点击/按键）、播放控制、
  进度条、倍速滑杆 + 预设、起始位置、操作预览（只渲前 300 条）。
- **设置页**：快捷键、移动采样阈值、压缩开关、运行权限、使用提示（整页可滚动）。

### 8.1 主题化对话框（不用原生 messagebox）

`tkinter.messagebox` 是系统原生控件，系统主题与界面深色主题不一致时非常突兀。
`src/dialogs.py` 用 CustomTkinter 实现了一套等效的模态对话框：标题 + 图标 + 正文 +
按钮，样式与主界面完全一致（`info / success / warning / error / confirm`）。

自动化友好：`set_suppress(True)`（或环境变量 `KMR_NO_DIALOG=1`）后，
所有对话框变成记录型空操作，不弹窗也不阻塞。
`confirm` 在抑制模式下的返回值可单独指定（默认 False）——
没有真人可问时，「不继续」永远是安全的一侧。

### 8.2 预览用原生 tk.Text 而不是 CTkTextbox

这是有意选择。CustomTkinter 的 `CTkTextbox` 内部有一个 200ms 的
`_check_if_scrollbars_needed` 自轮询，用来动态显隐滚动条。
脚本预览是只读文本，不需要这套逻辑：少一个轮询就少一份常驻开销
（符合「空闲时近乎零占用」），也避免它在窗口销毁后仍触发回调报错。
滚动条用 `CTkScrollbar` 手工接上 `yview` / `yscrollcommand`，外观不受影响。

### 8.3 退出时的 Tcl 报错（已修）

CustomTkinter 排了若干 `after` 回调，但 `destroy()` 里没有取消它们：

- `after(200, _windows_set_titlebar_icon)`
- `after(1000, _set_scaled_min_max)`
- `scaling_tracker` 的周期性 `check_dpi_scaling`
- `appearance_mode_tracker` 的 30ms `update` 自轮询

窗口销毁后它们照常被 Tcl 触发，去访问已不存在的命令，
往 stderr 刷 `invalid command name "..._windows_set_titlebar_icon"`。
`winapi.cancel_stale_tk_timers()` 精确取消这几个已知回调（其余内部定时器
保持不动，否则会破坏 CustomTkinter 自己的清理），并清理
`AppearanceModeTracker` 类级的窗口列表与 `update_loop_running` 标志位
（不清会让之后新建的窗口再也启动不了外观轮询）。

> 踩坑记录：一开始把 `<lambda>` 也加进要取消的特征串，结果
> `CTkTextbox` 等控件的内部 lambda 被误杀，`destroy()` 反而抛
> `can't delete Tcl command`。特征串必须精确，宁可少取消也不要误伤。

### 8.4 界面自身排的定时器要自己管

`App._after(fn, ms)` 统一登记本程序排的定时器，退出时逐个取消，
避免它们在控件销毁后仍去访问控件。回调里也都先判断 `self._closing`。

## 8.5 启动时自动提权

目标程序若以管理员运行，UIPI 会阻断低完整性进程与它的输入交换。因此程序
**在创建任何窗口之前**就完成提权（`src/elevation.py`）：

```
双击 exe
  → set_dpi_awareness()
  → is_elevated()? 否
  → ShellExecuteW("runas", 自己)  ← 系统 UAC 确认框在此出现
  → 旧进程立即 return 0 退出
  → 新进程（管理员）创建界面
```

关键点是**先提权、后建窗**。如果顺序反了，用户会先看到一个普通权限的窗口，
提权成功后第二个窗口再出现，观感很差。`selftest_boot.py` 专门守住这条顺序：
它替换掉入口里的窗口创建函数，断言在「需要提权」的分支下**一次都没有被调用**。

防无限重启：拉起子进程时会带上 `--elevation-attempted`，
新进程看到该标记就跳过提权。若用户拒绝 UAC 或子进程拉起失败，
程序仍以普通权限正常启动，并在侧栏与设置页显示当前权限状态，
附带「以管理员身份重新启动」按钮。

`--no-elevate` 可显式跳过（调试用）；`--check` 自检不触发提权，因为自检
不注入任何输入，普通权限即可完成。

无法绕过的是系统 UAC 确认框本身——那是 Windows 的安全边界。
想让它由系统在进程启动前处理，可在 `build.spec` 里把 `uac_admin` 设为 `True`
（清单声明 `requireAdministrator`）。本项目默认 `False`，原因是：
清单方式下用户拒绝 UAC 时程序完全无法启动，且不利于自动化验证；
而运行时方式保留了「拒绝后仍能用」的退路。两者对外观的影响是一样的——
都不会多出一个窗口。

## 9. 打包

PyInstaller 单文件模式，无控制台。`dist/KeyMouseReplayer.exe` 约 12.7 MB。

- 显式 `collect_data_files("customtkinter")` 收集主题 json 与图标字体，
  漏掉会让打包后界面渲染异常。
- 排除 `numpy / PIL / matplotlib / PyQt / PySide` 等用不到的重库（`excludes`），
  显著缩小体积。
- `version_info.txt` 写入 exe 版本信息，与 `src/version.py` 保持一致。

### 打包后无法自动验证的坑

单文件 exe 运行时要先把内容解压到 `%TEMP%\_MEIxxxx`。
在受限环境（安全软件、沙箱）里这一步会被拒绝：

```
[PYI-xxxx:ERROR] Failed to extract VCRUNTIME140.dll: failed to open target file!
fopen: Permission denied
```

这是**运行环境的限制，不是程序缺陷**。验证方法是改用 onedir 模式编译
（不需要解压）跑同一套自检，或在普通桌面环境下运行 exe。
本项目两种方式都验证过：onedir 直接通过，onefile 在解除限制后同样全部通过。

### `--check` 自检模式

无控制台程序看不到报错，因此内置自检：

```powershell
dist\KeyMouseReplayer.exe --check --out result.json
```

覆盖打包后最易出问题的 11 项：模块导入、CustomTkinter 资源、Tk 窗口渲染、
全局钩子安装、脚本序列化往返、坐标换算、回放时间轴精度、主界面构建、
主题化对话框、提权检查接口、自带资源。

### 自检踩的坑：对话框抑制必须用对模块

界面改用主题化 `dialogs` 之后，自检里原来那段 patch `tkinter.messagebox` 的
代码就失效了——「启动自检」弹出的是真正的模态框，把自检永久挂住。
更隐蔽的是：我在开发时习惯性设了 `KMR_NO_DIALOG=1`，于是源码运行一切正常，
直到跑打包后的 exe（没有那个环境变量）才暴露。
现在 `selfcheck.run()` 开头统一调用 `dialogs.set_suppress(True)`，
不再依赖任何环境变量。

教训：**验证要跑与用户一致的路径**，别让便利的调试开关掩盖真实行为。

## 10. 性能汇总

| 指标 | 数值 |
| --- | --- |
| 空闲 CPU | ~0%（消息循环阻塞等待，无轮询） |
| 空闲内存 | 30~40 MB（Tk + 界面） |
| 常驻轮询 | 只有 UI 队列泵（25ms）与录制计时刷新（60ms），都不做重活 |
| 录制开销 | 约 1.4% CPU（自旋窗口上限），每条 <1ms |
| 事件内存 | 24 字节/条 |
| 落点精度 | 中位 0.16ms，P99 0.5ms |
| 时间轴漂移 | 零累积 |
